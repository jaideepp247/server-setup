# server-setup

Put a Node.js app on a fresh Ubuntu server with one command. The script asks simple questions and does the rest, so no technical background is needed.

**New here?** Follow the step-by-step guide: [Server-Setup-Instructions.pdf](Server-Setup-Instructions.pdf)

## Quick start

1. Create an Ubuntu server with ports 22, 80 and 443 open to `0.0.0.0/0`. On AWS, `t4g.medium` or `t3.medium` suits most apps, and `t4g.small` works for small ones.
2. Connect to the server and run:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/jaideepp247/server-setup/main/setup.sh)
```

## What it does

| Step | What happens | What you provide |
|---|---|---|
| 1. Install | Installs Node 24, npm, yarn and pm2 | Nothing |
| 2. Get code | Clones your repo | Repo link, GitHub token, branch |
| 3. Settings | Saves your `.env` file | The env file, pasted all at once |
| 4. Build | Reads `package.json`, then installs and builds | Confirm the commands |
| 5. Start | Starts the app in pm2 with the repo's name, finds its port and checks it works | Nothing, unless the app fails |
| 6. CI/CD | Optional automatic deploys | Gitleaks key, SSH key (or let it create one) |
| 7. Pipeline | Adds GitHub secrets and the workflow file | Nothing |
| 8. Domain | Optional domain with HTTPS through Caddy | Your domain |

If the app fails to start, the script shows its errors with a plain-English hint and lets you paste the env file again.

It's safe to run again on the same server. It updates the existing app and can keep its `.env`.

## What you need

- Ubuntu (24.04 recommended) with `sudo` access
- A Node.js app on GitHub with `package.json` in the main folder
- A GitHub token, unless the repo is public and you skip CI/CD

### GitHub token permissions

Create a [fine-grained token](https://github.com/settings/personal-access-tokens/new) limited to your repo, with these repository permissions:

| Permission | Access | Needed for |
|---|---|---|
| Contents | Read and write | Cloning and adding the workflow file |
| Secrets | Read and write | Saving the deploy secrets |
| Workflows | Read and write | Adding the workflow file |

Without CI/CD, read-only **Contents** access is enough.

## How commands are chosen

| Item | Rule |
|---|---|
| Package manager | `packageManager` in `package.json`, then the lockfile, then yarn |
| Build | The `build` script, if there is one |
| Start | The first of `start:prod`, `start:production`, `prod`, `start`, `serve`, `preview` |

You can change these before anything runs.

## What it sets up

| Item | Location |
|---|---|
| App | `~/<repo-name>` |
| Env file | `~/<repo-name>/.env` (readable by your user only) |
| pm2 process | Named after the repo, restarts with the server |
| Pipeline | `.github/workflows/staging.yml` in your repo |
| GitHub secrets | `DEV_HOST`, `DEV_USERNAME`, `DEV_SSH_KEY`, `GITLEAKS_LICENSE` |
| Caddy site | `/etc/caddy/sites/<repo-name>.caddy` |
| Setup log | `~/server-setup.log` |

## Security

- The GitHub token stays in memory while the script runs. It isn't saved on the server.
- An SSH key created by the script goes into GitHub secrets, and its private half is then removed from the server.
- Your env values are never written to the setup log.
- Port 22 is open to the internet because GitHub's deploy runners don't use fixed IP addresses. Login is by SSH key only.

## Good to know

- **No domain:** the app runs, but it can't be opened from outside unless you also open its port in your cloud firewall.
- **Fixed IP:** give the server one (an Elastic IP on AWS). Otherwise the address can change, which breaks your domain and automatic deploys.
- **Cloudflare:** set the DNS record to "DNS only" (grey cloud) during setup.
